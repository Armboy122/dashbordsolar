# Domain rules — ความหมายและความถูกต้อง

สถานะ: ข้อกำหนดเป้าหมาย; เกณฑ์เชิงตัวเลขใหม่ยังไม่อนุมัติใช้จริง

## แหล่งข้อมูลและเวลา
ข้อมูลหลักเป็น Huawei Plant Report รายเดือน ไม่ใช่ telemetry สด แยกเดือนรายงาน เวลาได้รับไฟล์ และเวลานำเข้าสำเร็จ ใช้ Asia/Bangkok ในการเลือกเดือน เดือนที่ยังไม่จบต้องติดป้ายข้อมูลระหว่างเดือน ห้ามเทียบยอดเต็มเดือนกับบางเดือนโดยไม่อธิบาย

ตัวดาวน์โหลด/นำเข้ามีแล้วตาม [คู่มือ sync](fusionsolar-sync.md) แต่ยังไม่มี scheduler และหน้าแก้รายเดือนครบวงจร เอกสารนี้ไม่ถือว่าเปิดใช้งานสิ่งเหล่านั้นแล้ว

## เอกลักษณ์ไซต์และการนับ
- ปัจจุบันใช้ชื่อไซต์และขอบเขตทะเบียนที่ยืนยันจากการนำเข้า; stable site ID และ alias เป็นงานที่ต้องออกแบบก่อนรวม/เปลี่ยนชื่อ
- จำนวนไซต์คำนวณจากเอกลักษณ์ในขอบเขต ไม่ hardcode 72
- ไฟล์ ก.พ. 2026 ที่ตรวจแล้วมี 72 ชื่อไม่ซ้ำ; ประวัติรวมมีชื่อเพิ่มเติม ห้ามลบเพื่อให้ยอดเท่ากัน
- แยกจำนวนไซต์ในทะเบียน จำนวนไซต์มีรายงาน จำนวนไซต์มีผลผลิต และจำนวนไซต์ไม่มีผลผลิตวัดได้
- ตาราง KPI และกราฟใช้ขอบเขตเดียวกัน; search/filter เปลี่ยนจำนวนที่แสดง ไม่เปลี่ยนฐานรวมโดยเงียบ
- เดือนทะเบียนต้นทางไม่ยืนยันว่าวันนี้ไซต์ยังเปิดใช้งาน ข้อมูลสถานะต้องมีแหล่งที่มาและช่วงเวลาที่มีผล ห้ามอนุมานจากวงเล็บในชื่อไซต์อย่างเดียว

## ค่าพลังงาน
- ใช้ inverter yield เป็นตัวชี้วัดผลผลิตหลักตาม dashboard ปัจจุบัน ระบุ source field ชัดเจน ไม่สลับกับ PV yield เงียบ ๆ
- null = ไม่มีค่าที่ใช้ได้; 0 = ต้นทางรายงานศูนย์; ค่าที่ถูกปฏิเสธต้องมีเหตุผล ทั้งสามไม่ใช่สิ่งเดียวกัน
- kWh คือพลังงาน; kW คือกำลัง; kWp คือกำลังติดตั้ง ไม่ใช้แทนกัน
- ค่า Self-consumption Rate (%) ต้นทาง/ฐานข้อมูลเป็น percentage points; API ที่ formatter รับ fraction ต้องหาร 100 ครั้งเดียว เช่น 97.651 → 0.97651 → 97.651% และ 0.886 → 0.00886 → 0.886%
- สัดส่วนจากรายงานที่ไม่สอดคล้องกับค่าพลังงานต้องติดป้าย/ตรวจสอบ ไม่แทนด้วยค่าที่คาดเดา
- ยอดรวมที่ขาดบางไซต์ต้องบอกความครบถ้วน ไม่ถือว่า missing เท่ากับ zero
- ไม่แสดงเงินประหยัดหรือผลตอบแทนแน่นอนหากไม่มีอัตราค่าไฟ วิธีคำนวณและข้อมูลที่เหมาะสม

## การเปรียบเทียบ
เปอร์เซ็นต์เปลี่ยน = (ค่าปัจจุบัน − ฐาน) / ฐาน × 100 เมื่อฐานเป็นบวกและข้อมูลเปรียบเทียบได้ ถ้าฐานเป็นศูนย์/ขาด ให้แสดงว่าเทียบเปอร์เซ็นต์ไม่ได้และใช้ผลต่างหน่วยแทนเมื่อทำได้

แสดงชนิด baseline เสมอ: เดือนก่อน / เดือนเดียวกันปีก่อน / ค่าเฉลี่ยช่วงที่ระบุ พิจารณาจำนวนวัน ความครบถ้วน ฤดูกาล การเปลี่ยนกำลังติดตั้งและช่วงหยุดตามแผน ไม่มีข้อมูลอากาศก็ห้ามอ้างว่าอากาศเป็นสาเหตุที่ยืนยันแล้ว

การเทียบข้ามไซต์ต้องมี capacity ที่เชื่อถือได้และกลุ่มที่เปรียบเทียบได้ kWh/kWp เพียงอย่างเดียวไม่พิสูจน์ความเสียหาย การเปรียบเทียบยอดรวมควรใช้กลุ่มไซต์ที่มีข้อมูลทั้งสองช่วง หรือแจ้งความต่างของความครอบคลุมชัดเจน

## มิติของสถานะ
1. ความสำคัญ: เร่งตรวจสอบ / ควรตรวจสอบ / เฝ้าติดตาม / ไม่พบสัญญาณผิดปกติ
2. คุณภาพข้อมูล: ครบตามที่ใช้ประเมิน / ขาดรายงาน / ขาดค่าจำเป็น / ค่าขัดกัน / รอยืนยัน
3. สถานะเปิดใช้งาน: เปิดใช้งาน / ยังไม่เปิดใช้งาน / หยุดตามแผน / ไม่ทราบ โดยมีช่วงเวลาและหลักฐาน
4. การติดตามและผลลัพธ์: ตาม [UX](ux.md)

ข้อมูลไม่พออาจไม่มีระดับความสำคัญที่ประเมินได้ ต้องแสดง “ยังประเมินไม่ได้” ไม่จัดเป็นปกติ; ปัญหาข้อมูลเองอาจต้องรีบตรวจแต่ต้องติดประเภทว่าเป็นปัญหาข้อมูล

## หลักการกำหนดความสำคัญใหม่
- เร่งตรวจสอบ: ตัวอย่างคือศูนย์ทั้งเดือนที่ข้อมูลครบ เคยผลิต และไม่มีเหตุหยุดที่ทราบ ต้องยืนยันเงื่อนไขก่อน ไม่ใช่ศูนย์ทุกกรณี
- ควรตรวจสอบ: ลดลงมากหรือเกิดซ้ำและมีหลักฐานพอให้ตรวจต่อ
- เฝ้าติดตาม: แนวโน้มเริ่มเปลี่ยนแต่ยังไม่พอให้สรุป
- ไม่พบสัญญาณผิดปกติ: ประเมินได้และไม่เข้าเงื่อนไข ไม่รับรองสุขภาพอุปกรณ์

เกณฑ์ลดลงกี่เปอร์เซ็นต์ ต่อเนื่องกี่เดือน baseline ขั้นต่ำ น้ำหนักคะแนน และ tolerance ข้อมูลขัดกัน ยังต้องทดสอบย้อนหลังและให้ช่างทบทวน ห้าม Kimi หรือผู้พัฒนาใส่ค่าขึ้นเองเป็นนโยบายจริง

ระบบเดิมมี scoring หลายบริบท เช่น src/lib/scoring.ts และกติกา historical ในส่วนวิเคราะห์/แสดงผล บางส่วนยังรวม missing กับ zero ห้ามเปลี่ยนแค่ชื่อระดับแล้วอ้างว่าตรงกับกติกาใหม่นี้ ต้องสำรวจจุดคำนวณทั้งหมด ทำ mapping ที่ชัดเจน และทดสอบก่อนย้าย ระหว่างต้นแบบใช้ตัวอย่างที่ติดป้ายหรือระบุว่าเป็นการประเมินเดิม

ทุกผลประเมินใหม่ควรเก็บ rule version, ข้อมูล/รุ่นที่ใช้, baseline, เหตุผล และเวลาประเมิน เพื่ออธิบายผลย้อนหลังได้ การปรับระดับเองเก็บค่าที่ระบบเสนอแยกจากค่าผู้ดูแลพร้อมเหตุผล

## ผลตรวจและการปิดเรื่อง
หนึ่งไซต์มีหลายประเภทปัญหาได้ จำนวนไซต์ผิดปกติจึงไม่เท่าจำนวนงาน ใช้ stable site identity + ประเภทปัญหา + งานที่ยังไม่จบเพื่อตรวจการซ้ำ เพิ่มหลักฐานข้ามเดือนในงานเดิม เก็บความสัมพันธ์เมื่อเปิดใหม่หลังเคยปิด

“แจ้งช่างแล้ว” เป็นการบันทึกของผู้ดูแล ไม่ใช่การยืนยันว่า LINE ส่งสำเร็จ “ช่างแจ้งว่าแก้แล้ว” ไม่ใช่ยืนยันจบ ต้องมีผู้บันทึกหลักฐาน/เหตุผลการยืนยัน การฟื้นตัวเดือนถัดไปใช้ประกอบแต่ไม่พิสูจน์สาเหตุด้วยตัวเอง ไม่ปิดงานอัตโนมัติเพียงเพราะไซต์หายจากไฟล์

## นำเข้าและแก้ไขย้อนหลัง
เก็บค่าต้นทางแยกค่าที่ใช้จริง พร้อม source hash, เดือนและ audit นำเข้าซ้ำไม่สร้าง site/month ซ้ำ ไม่ลบไซต์ที่ไม่พบในไฟล์ครั้งใหม่ การดาวน์โหลดไม่สำเร็จต้องไม่รายงานว่าอัปเดตสำเร็จ

การแก้รายเดือนต้องมี old/new value, หน่วย, เหตุผล, ผู้แก้, เวลา, รุ่นข้อมูล และการป้องกันการเขียนทับพร้อมกัน การ sync ต้องรักษาค่าที่ผู้ใช้แก้ไว้และเสนอ conflict ให้ทบทวน ปุ่มกลับไปใช้ค่าต้นทางเป็นการกระทำชัดเจนมีประวัติ เมื่อแก้ให้ประเมินเดือนที่เกี่ยวข้องและ baseline ที่พึ่งพาใหม่ โดยไม่ลบประวัติผลตรวจช่าง

ข้อกำหนดสิทธิ์ผู้แก้และการจัดเก็บรูปยังต้องออกแบบ ไม่แสดง form ว่าบันทึกถาวรได้ก่อนมี storage/API จริง ไม่เก็บบัญชี Huawei, password หรือ session ในเอกสาร prompt หรือ frontend

## กรณีทดสอบก่อนเปิดใช้กติกาใหม่
missing report vs null yield vs zero; zero บนไซต์ยังไม่เปิด; หยุดตามแผน; baseline zero/ขาด; เดือนบางส่วน; เปลี่ยน capacity; ขอบเขตไซต์ต่างกัน; 72 source vs historical; เปอร์เซ็นต์ต่ำกว่า 1%; source/manual conflict; import ซ้ำ; แก้ย้อนหลัง; งานเดิมข้ามเดือน; ปัญหาใหม่หลังปิด; rule version เปลี่ยน; failed sync ไม่กลายเป็นยอดศูนย์

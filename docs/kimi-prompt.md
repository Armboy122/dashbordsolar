# ส่งงานออกแบบให้ pi / Kimi K3

ใช้ข้อความด้านล่างใน pi โดยเลือก provider/model ที่ตั้งค่าไว้สำหรับ Kimi K3 ก่อน ชื่อ provider/model ต้องตรวจจากเครื่องที่ใช้ ไม่ใส่ข้อมูลล็อกอินลงใน prompt นี้

งานรอบแรกคือออกแบบต้นแบบให้ตรวจได้ ไม่ใช่เปิดใช้กติกาประเมินใหม่หรือระบบติดตามที่ยังไม่มี backend

## Prompt พร้อมคัดลอก

```text
คุณช่วยออกแบบ UX/UI ใหม่ของ AnalysisSolar ใน repository นี้ โดยใช้ Kimi K3 ผ่าน pi coding

อ่าน AGENTS.md ที่มีผลกับ repository และอ่านเอกสารตามลำดับ:
1. design.md
2. docs/ux.md
3. docs/ui.md
4. docs/domain-rules.md
5. docs/site-count-correction.md และ docs/fusionsolar-sync.md เพื่อเข้าใจสิ่งที่ทำได้จริง
ใช้เอกสารชุดใหม่นี้เป็นข้อกำหนด UX/UI ล่าสุด

ผู้ใช้เป็นผู้ดูแลโซลาร์ที่ไม่เชี่ยวชาญเทคนิค ตรวจข้อมูลรายเดือน ส่งให้ช่างผ่าน LINE และต้องการรู้ว่าพบอะไร ควรตรวจอย่างไร และช่างพบสาเหตุอะไร ผู้ใช้ยังชอบกราฟและแดชบอร์ดมาก

รอบนี้ให้สร้างต้นแบบที่รันและเปิดดูได้ของ 4 หน้า: ภาพรวม / ไซต์ทั้งหมดพร้อมรายละเอียด / รายการตรวจสอบ / รายงานและข้อมูล เริ่มจากสำรวจ component, API, chart, routing และ worktree ปัจจุบัน แล้วทำแผนสั้น ๆ ก่อนลงมือ รักษางานที่แก้ค้างไว้ ห้าม reset หรือเขียนทับงานอื่น

หน้าแรกต้องมีเดือน/ความครบถ้วน KPI กราฟย้อนหลัง 12 เดือน และรายการสำคัญที่กดดูหลักฐานได้ รายละเอียดปัญหาแยกข้อเท็จจริง สาเหตุที่เป็นไปได้ และวิธีตรวจต่อ แยกความสำคัญจากสถานะงานและคุณภาพข้อมูล มีตัวอย่าง flow คัดลอก LINE และบันทึกผลตรวจแบบสั้น รองรับชื่อไซต์ภาษาไทยยาวและมือถือ 390px

ใช้ข้อมูลจริงจาก API เท่าที่มี หากความสามารถใดยังไม่มี backend ให้ทำต้นแบบแยกและติดป้ายข้อมูลตัวอย่าง/ยังไม่บันทึกจริงอย่างชัดเจน อย่าสร้างผลตรวจช่างหรือสถานะ sync สำเร็จปลอมในหน้าข้อมูลจริง ปุ่มคัดลอกข้อความต้องไม่ส่ง LINE และไม่เปลี่ยนสถานะเป็นแจ้งแล้วเอง

อย่าเปลี่ยนสูตร scoring เกณฑ์แจ้งเตือน schema หรือค่าฐานข้อมูลในรอบออกแบบนี้ กติกาความสำคัญใหม่ยังมีเกณฑ์ตัวเลขที่ต้องทดสอบ อย่า map ชื่อสถานะเดิมไปชื่อใหม่โดยอ้างว่าประเมินตรงกันแล้ว ถ้าต้องการ API เพิ่มให้เขียนข้อเสนอแยกพร้อมเหตุผล ห้ามตั้ง scheduler, เปิด public tunnel, deploy, commit/push หรือใช้บัญชี Huawei ในงานรอบนี้

รักษาความถูกต้อง: null ไม่ใช่ 0; จำนวนไซต์ไม่ hardcode; scope ของตาราง/KPI/กราฟตรงกัน; เดือนและ scope คงอยู่เมื่อเข้าออกไซต์; แสดงความครบถ้วนและเดือนต้นทาง; เปอร์เซ็นต์แปลงครั้งเดียว; ไม่เรียกข้อมูลรายเดือนว่าสถานะสด ไม่รับรองว่าอุปกรณ์เสียหรือปกติแน่นอน

UI ใช้พื้นกลาง อ่านไทยง่าย สีสถานะแตกต่างพร้อมข้อความ/ไอคอน กราฟมีสีและรูปแบบเส้นแยกกัน มือถือใช้การ์ดสำหรับรายการหลัก ไม่บีบตารางกว้างหรือซ่อน overflow ทั้งหน้า รองรับ keyboard, focus, loading, error, empty, partial data และชื่อยาว

ส่งมอบต้นแบบ runnable พร้อมสรุปสิ่งที่ทำจริง/จำลอง/ยังขาด ตรวจ desktop 1440px และ mobile 390px บันทึกภาพแต่ละหน้าในพื้นที่ artifact ของโปรเจกต์ รัน checks ที่เหมาะกับ code ที่แก้และรายงานผลจริง ระบุข้อเสนอ backend/กติกาที่ต้องทำต่อแยกต่างหาก อย่าอ้างว่าทดสอบผ่านหากไม่ได้รัน
```

## วิธีตรวจงานที่ได้รับ
- เทียบกับเกณฑ์ตรวจรับใน ux.md และ ui.md ไม่ตัดสินเฉพาะความสวย
- ตรวจว่า dashboard/กราฟยังตอบโจทย์ และจากรายการเข้าถึงหลักฐานได้
- ตรวจว่าไม่มีสถานะหรือการบันทึกปลอมปะปนกับข้อมูลจริง
- ทบทวนภาพมือถือและ desktop ก่อนเริ่มงาน backend และก่อนเปลี่ยนกติกาประเมิน

ไฟล์นี้เป็น prompt ที่เตรียมไว้ ยังไม่ใช่หลักฐานว่าส่งให้ pi หรือ Kimi ทำงานแล้ว
